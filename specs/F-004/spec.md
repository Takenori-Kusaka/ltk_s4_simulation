# F-004 試合結果の入力(本番・スクリム)

## 背景

作者は、大会(2026-10-15〜11-22)の本番の結果と、開幕前と大会中のスクリムの結果を入れて、予測と評価を試合日ごとに更新したい。企画書は「実際の試合結果の入力と、それによる予測の更新」をコア機能の候補に挙げている(`docs/project-brief.md`)。

結果を読む側は 3 つある。F-005 は本番の結果から補正 θ を当て直し(F-005 基準 4)、連敗の数 k で気持ちの補正を加え(基準 11)、試合の分析ページに予測と実際を並べる(基準 8)。F-009 は直近の試合の記録(`GameRecord`)から対面との差で軸の補正を作る(F-009 基準 6〜8)。F-014 の根拠のストーリーは個人の行に印を出せる。この機能は、結果を記録する形と置き場、検証、各機能へ渡す経路を決め、公開の画面に出す。

### 価値責任者の方向(2026-10-11)

- スクリムは「チャレンジ・調整・練習・確認」の場で、本番の試合結果に大きくは影響しない。ただし **地力の評価、ピックプールの評価、キーマンの発見**には有用
- リスナー参加のスクリムはデータとして扱わない
- スクリム中の文字起こしは話者分離が無いため、コール力の根拠としては本人を特定できる箇所に限り確度「低」
- 本番の結果(Regular Stage 以降)は F-005 の補正 θ と連敗 k(気持ちの補正)の入力になる

この仕様の数値(`scrimGameWeight` 2.0、F-005 の `weights.scrim` を 0 にする起案、キーマンの印の規則)は AI の起案であり、**価値責任者の確定を要する**。

### 最初の事例(2026-10-10 のスクリム)

LR CORE SUP 千燈ゆうひの配信(https://www.youtube.com/watch?v=AZbkNH5Z5-I )の結果画面から、LR CORE 対 DD CORE のスクリム 3 試合(配信内の 4〜6 試合目。3 試合とも DD CORE の勝ち)を書き起こした(`data/scrim/2026-10-10-lr-core-vs-dd-core.json`。手法は `data/scrim/METHOD.md`)。各試合に勝敗・試合時間・10 人のチャンピオンと K/D/A・ゴールド・ダメージ、名簿との対応づけと確度がある。DD CORE の JG・MID・SUP のチャンピオンは顔出し枠で隠れて読めない試合があり、LR CORE ADC の対応づけは表示名が違うため「推定」である。この仕様の記録の形は、この JSON に合わせる。

## 用語

- **試合結果の記録**: 1 試合(1 ゲーム)の結果を 1 要素とする JSON。本番の記録とスクリムの記録の 2 種類
- **本番の記録**: 大会の公式の試合(Regular Stage の NEXT・CORE 各 24 試合、MASTERS CUP の各回の準決勝 2 試合・3 位決定戦・決勝の各ゲーム、Playoffs の各マッチの各ゲーム)の記録。置き場は `docs/research/grounds/results/`
- **スクリムの記録**: 大会の 2 つの階級チームが、大会の外で行った 5 対 5 の練習試合の記録。置き場は `docs/research/grounds/scrims/`
- **記録のファイル**: `<YYYY-MM-DD>-<識別子>.json`(識別子は小文字の英数字とハイフン。例 `2026-10-10-lr-core-vs-dd-core.json`)。配列で 1 試合 1 要素。同じ日・同じ組の試合を 1 ファイルにまとめる
- **階級チーム**: 記録の中では `<チーム> <階級>`(例 `DD CORE`)。階級チーム ID は `DD-CORE`(名簿 `src/data/roster.ts` の `team` と `tier`)
- **記録の出典** `source`: `url`(配信のアーカイブの URL、または公式の結果ページの URL)を必ず持つ。配信なら結果画面の時刻 `resultScreenSec`(秒)を持つ。出典の無い記録は受け付けない
- **対応づけの確度** `mappingConfidence`: 「確信」「推定」「未確認」のどれかで始まる文字列。括弧の中に理由を書いてよい(例 `推定(リザルト画面の表示名が違う。同じ席・同じチャンピオン)`)
- **リスナー参加のスクリム**: `listeners` が true の記録。対象外
- **対面**: 同じ試合の相手チームの同じロールの選手
- **チャンピオンの一覧**: F-003 の `data/public/champions.json`(Data Dragon ja_JP)に、チャンピオンごとの数値の key を `keys`(例 `"Aatrox": 266`)として足したもの。記録の `champion`(日本語名)を key に引く。F-009 のピックプールの `championId` と同じ値
- **スクリムの試合の記録(GameRecord)**: スクリムの選手 1 人の 1 試合分を、F-009 の「評価の試合」と同じ形 `GameRecord`(`src/rating/types.ts`)にしたもの。下の「指標の対応表」で作る
- **スクリムの重み `scrimGameWeight`**: F-009 の評価設定 `src/rating/config.json` の `engine.scrimGameWeight`。スクリムの試合の記録の新しさの重みに掛ける係数。初期値 2.0(ソロランク 1 試合の 2 倍。AI の起案、価値責任者の確定を要する)
- **連敗の数 k・補正 θ・気持ちの補正**: F-005 の用語のとおり
- **予測**: その試合について、試合日より前に計算した最新の勝率表(`data/public/winrates.json` の `computedAt` が試合日の 0 時(JST)より前のもの)の、その試合の両チームの勝率(`pA`・`pB`)
- **キル関与**: (キル + アシスト) ÷ チームのキル。チームのキルが 0 なら 0
- **キーマンの印**: スクリムで「ダメージ最多」「キル関与最多」だった試合の数から付ける表示だけの印。点数には入れない
- **日程の順**: 同じ試合日の本番の試合の並び。Regular Stage は日程(`src/sim/schedule.ts` の `REGULAR_DAYS`)のカードの順に、各カードは NEXT → CORE。MASTERS CUP は semi1 → semi2 → third → final で、final は G1 → G2 → G3。Playoffs は upperFinal → lowerSemi(2026-11-21)、lowerFinal → grandFinal(2026-11-22)で、各マッチは G1 → G4
- **試合 ID** `matchId`: Regular Stage は `RS-<日>-<ブルー>-<レッド>-<階級>`(例 `RS-1-CC-DD-NEXT`。F-006 と同じ形)、MASTERS CUP は `MC<回>-<試合>-G<n>`(試合は `semi1`・`semi2`・`third`・`final`)、Playoffs は `PO-<マッチ>-G<n>`(マッチは `upperFinal`・`lowerSemi`・`lowerFinal`・`grandFinal`)、スクリムは `SC-<YYYYMMDD>-<階級チーム ID>-<階級チーム ID>-G<n>`(2 つの ID は辞書順、n は同じ日・同じ組の記録の通し番号)

### 指標の対応表(スクリムの記録 → F-009 の指標のキー)

| 記録の欄 | F-009 の指標のキー | 使う軸 |
| --- | --- | --- |
| `damage` | `totalDamageDealtToChampions` | 地力(対面との比の対数)、集団戦の材料 |
| `goldPerMin`(無ければ `gold` ÷ 試合時間(分)) | `goldPerMinute` | 地力 |
| `deaths` | `deaths` | 安定感 |
| `kills`・`assists` | `kills`・`assists` | 記録として持つ |
| (`kills` + `assists`) ÷ チームの `kills` | `killParticipation` | 連携 |
| `damage` ÷ チームの 5 人の `damage` の合計 | `teamDamagePercentage` | 集団戦(MID・ADC) |
| `gold` | `goldEarned` | 記録として持つ |
| `cs`(あれば) | `totalMinionsKilled` | 記録として持つ |
| `level`(あれば) | `champLevel` | 記録として持つ |
| 勝敗(`winner` がその選手のチームか) | `win`(1 / 0) | ピックプールの勝率 |
| `champion`(日本語名 → チャンピオンの一覧の key) | `championId` | ピックプール |

対応表に無い指標(`soloKills`、`maxCsAdvantageOnLaneOpponent`、`laningPhaseGoldExpAdvantage`、`enemyChampionImmobilizations`、`pickKillWithAlly`、`damageTakenOnTeamPercentage`、視界の指標)は持たない。F-009 基準 8 の規則で、その指標はその試合で除外され、軸に使える指標が 1 つも無い試合はその軸で除外される。レーン戦の軸は 14 分の値を要するため、スクリムの試合は効かない。

## 受入基準

### 入力と検証

| # | 型 | 受入基準 |
| --- | --- | --- |
| 1 | ユビキタス | システムは試合結果の記録を、本番は `docs/research/grounds/results/`、スクリムは `docs/research/grounds/scrims/` の `<YYYY-MM-DD>-<識別子>.json`(配列。1 試合 1 要素)から読み、各要素が `kind`(`official` / `scrim`)・`date`・`duration`(`mm:ss`)・`winner`・`teams`(2 つの階級チーム。各チームに `kills`・`deaths`・`assists`・`gold` と 5 人の `players`)・`source`(`url` を持つ)・`listeners`(真偽値)を持ち、各選手の行が `role`・`rosterName`・`mappingConfidence`・`champion`(日本語名か null)・`kills`・`deaths`・`assists`・`gold`・`damage` を持つことを検証しなければならない。本番の記録はさらに `stage`(`regular` / `masters` / `playoffs`)・`day`(Regular Stage は 1〜6、MASTERS CUP は回 1〜3、Playoffs は null)・`tier`(NEXT / CORE / MASTERS)・`match`・`game` を持つ |
| 2 | ユビキタス | システムは `kind` が置き場(results / scrims)と一致し、`date` がファイル名の日付と一致し、`winner` が `teams` の 2 つの階級チームのどちらかで、`rosterName` が名簿(`src/data/roster.ts`)の選手名と一致し、その選手の名簿の階級チームが行の属する階級チームで、`role` がその選手の名簿のロールと一致し、`champion` がチャンピオンの一覧の日本語名か null であることを検証しなければならない |
| 3 | ユビキタス | 本番の記録について、システムは `date`・`tier`・両階級チーム・`day`・`match` が公式の日程(`src/sim/schedule.ts` の `REGULAR_DAYS`・`MASTERS_CUPS`。Playoffs は 2026-11-21 と 2026-11-22)の試合と一致し、`sides` があれば日程のブルーとレッドに一致し、同じ試合 ID の記録が 1 件だけであることを検証しなければならない |
| 4 | 望ましくない事象 | 記録が基準 1〜3 のどれかに反する場合、または `source.url` が無い場合、システムはファイル名・要素の番号・反した欄を出力し、失敗の終了コードを返し、公開用のファイル(`ratings.json`・`winrates.json`・`results.json`)のどれも書いてはならない |
| 5 | 望ましくない事象 | `listeners` が true の記録がある場合、システムはその記録をどの計算にも使わず、ファイル名と要素の番号と「リスナー参加」を出力しなければならない |
| 6 | 望ましくない事象 | `mappingConfidence` が「未確認」で始まる選手の行がある場合、システムはその選手の試合の記録を作らず、その選手を対面とする相手の記録の対面を無し(F-009 基準 8 で除外)とし、選手名と「未確認」を出力しなければならない。「確信」「推定」の行は使い、「推定」の行の数を出力に示す |
| 7 | 望ましくない事象 | 同じ `date`・同じ 2 つの階級チーム・同じ `duration` のスクリムの記録が 2 件以上ある場合(2 本の配信から同じ試合を書き起こした場合)、システムはファイル名の辞書順で最初の 1 件だけを使い、残りのファイル名と要素の番号を「重複」として出力しなければならない |

### 本番の結果の使い方(F-005 の θ と k)

| # | 型 | 受入基準 |
| --- | --- | --- |
| 8 | ユビキタス | システムは本番の記録から、F-005 の結果の入力 `games[]`(`matchId`・`date`・`stage`・`day`・`tier`・`teams`(両階級チーム ID)・`winner`(階級チーム ID)・`kind: "official"`・`source`)を、試合日の昇順、同じ日は日程の順に並べて `data/public/results.json` に書かなければならない |
| 9 | ユビキタス | システムは階級チームごとに、連敗の数 k(その階級チームの直前の本番から遡って続いた負けの数。勝てば 0)と、本番の勝敗の並び(新しい順。例 `LLW`)を `results.json` の `teams[]` に書き、F-005 基準 11 の気持ちの補正(`src/winrate/dynamics.ts` の `dayShift` の `kA`・`kB`)に渡さなければならない。MASTERS CUP の決勝の各ゲームは 1 試合ずつ数える |
| 10 | イベント駆動 | 本番の記録が追加されたとき、システムは次の集計で勝率表(`data/public/winrates.json`)を本番の結果を含めて作り直し、`results` の欄に本番の試合数・スクリムの試合数・最新の試合日を書かなければならない。F-005 の θ の当て直し(F-005 基準 4)が実装されている場合はその入力に `games[]` を渡し、実装されていない間は θ を 0 のまま「データなし」とする(F-005 基準 4 の規則) |
| 11 | イベント駆動 | 本番の記録を初めて読んだ集計で、システムはその試合の予測(用語)を `games[].forecast`(両チームの勝率と、その勝率表の `computedAt`)として `results.json` に書き、以後の集計では前回の `results.json` の `forecast` を引き継いで書き換えてはならない。試合日より前に計算した勝率表が無い場合は `forecast` を null とし、理由「試合日より前の勝率表が無い」を書く |

### スクリムの結果の使い方(F-009 の個人の評価)

| # | 型 | 受入基準 |
| --- | --- | --- |
| 12 | ユビキタス | システムはスクリムの記録の各選手の行(基準 5〜7 で除いたものを除く)から、指標の対応表のとおりに F-009 の試合の記録(`GameRecord`。`queueId` は 0、`position` は名簿のロールの `teamPosition`、`endTime` は `date` の正午(JST)、`durationMin` は `duration` の分、`opp` は対面の行の同じ対応表の値)を作り、F-009 の評価の入力(`loadRatingInputs` の `games`)に、ソロランクの試合と同じ配列で足さなければならない |
| 13 | ユビキタス | システムはスクリムの試合の記録に、F-009 の新しさの重みに `scrimGameWeight`(初期値 2.0)を掛けた重みを付け、補正の重み付き平均・縮小の割合 n ÷ (n + k)・確度の有効な試合数 n を、その重みで数えなければならない(ソロランク 1 試合の重みは従来どおり 1 × 新しさの重み) |
| 14 | ユビキタス | システムはスクリムの試合の記録を、F-009 の評価の試合の条件(直近 120 日以内・10 分以上)と大会のロールの試合の条件(F-009 基準 2)に、ソロランクの試合と同じ規則で当てはめ、調子の係数(F-009 基準 17。ランクのキュー 420・440 だけ)にスクリムの試合を使ってはならない |
| 15 | ユビキタス | システムは選手の各データの軸の説明と確度の理由に「スクリム n 試合(重み w)を含む」(n はその軸に使ったスクリムの試合の数、w は `scrimGameWeight`)を示さなければならない。スクリムの試合が 0 件の軸にはこの文を出さない |
| 16 | ユビキタス | システムはピックプールの軸(F-009 基準 11)で、スクリムの使用チャンピオン(`champion` が null でない行)を大会のロールの試合 1 試合(勝敗つき)として数えなければならない(`scrimGameWeight` は掛けない)。`champion` が null の行は、チャンピオンの数にも試合の数にも数えない |
| 17 | 望ましくない事象 | スクリムの配信の文字起こしから作ったコール力の根拠(`docs/research/grounds/normalized/shotcalling.json` の `origin` が `scrim-transcript` で始まる項目)に、話者を本人と特定した印 `speakerIdentified: true` と時刻つきの URL が無い場合、システムはその根拠を読まず、選手 ID と理由を警告として出力しなければならない。読んだ根拠の確度は「低」とする(F-009 基準 15 の確度の決め方より優先) |

### スクリムの結果の使い方(キーマン・チームの層)

| # | 型 | 受入基準 |
