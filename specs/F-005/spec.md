# F-005 勝率の推定と試合ごとの分析

## 背景

作者は、大会の全試合を1試合ずつ開いて、どちらがどれだけの確率で勝つか、その根拠は何かを見たい(価値責任者の要望、2026-10-08)。Playoffs と Regular Stage のパフォーマンスの差も考慮したい。

F-001 は勝率表を入力として受け取るだけで、勝率そのものは作らない。この機能が、階級チームの戦力 S(F-010)と選手の8軸と調子(F-009)、確定した本番の結果とスクリムの結果(F-004)、ピックとプロテクトの予想(F-006)から、階級ごと・ステージごとの勝率表を作り、全試合の分析ページに出す。式と初期値の根拠は `docs/design/team-model-algorithm.md`(S1〜S3 の検証つきの起案)。

### 価値責任者の方向づけ(2026-10-09)

- 勝率の入力は、F-010 の階級チームの戦力 S(選手5人のロールの重み付きの総合 0.85 + コーチの総合 0.15)と、F-009 の8軸と調子の係数とする。旧 F-002 の5軸は使わない
- NEXT のプロテクトの予想(F-006)の勝率への効果は、相手の CORE が使えるピックを減らす効果(CORE は同じカードの直前の NEXT 戦で使われたチャンピオンを使えない規則)として、ドラフトの優位の項で勝率に反映する。初期値は AI の起案とし、K-08 で上限を確かめる

### 仕上がりの変化(価値責任者の備忘 2026-10-09)

チームの仕上がりと勝ち方は大会の中で段々と固まり、その速さや、負けが先行したときの気持ちの落ち込みで、試合が進むごとに強さが変わる。勝ち方やチームのスタイルがどれだけ早く見つかるかで結果は大きく変わる。仕上がりの速さは、(1) 過去に一緒にプレイしていたか(共同プレイ歴)と、(2) メタの近さ(以前と同じマクロで戦えるか)で差が出る。この特性を勝率の予想の計算に含める。

注意(AI の分析): `docs/design/team-model-algorithm.md` 節2.1 の検証では、「継続性」を固定の値として勝率に足すと係数の符号が定まらなかった(S3 の交差検証)。この備忘は固定の値ではなく、試合日とともに変わる強さ(仕上がりの曲線と、連敗による補正)として扱う。採用の前に S1〜S3 の試合日ごとの成績で当てはまりを確かめ、改善しない間は寄与を上限以内に抑えて確度「低」で表示する(基準13)。

## 用語

- **戦力 S**: F-010 の用語のとおり。NEXT・CORE は S = 0.85 × Σ w_r × O_r + 0.15 × C、MASTERS は S = Σ w_r × O_r。O_r は F-009 の8軸の表示の点数(調子の係数を加えた後)から作る選手の総合
- **評価設定**: `src/winrate/config.json`。この仕様の初期値を置く。値は AI の起案で、価値責任者・技術判断者が変えてよい
- **対数オッズ**: logit p = ln(p ÷ (1 − p))。勝率は p = 1 ÷ (1 + exp(−logit))
- **β(尺度)**: 階級ごとに、同じ階級の4チームの6組について β × (S_A − S_B) の標準偏差が 0.35 になる値。6組の差がすべて 0 なら β = 0
- **補正 θ**: 結果から推定する階級チームごとの補正。事前分布は平均 0・標準偏差 0.58 の正規分布
- **経過した試合日の数 d**: その試合より前に、その階級チームが本番を戦った試合日の数(Regular Stage・MASTERS CUP・Playoffs を通して数える)
- **共同プレイ歴 c**: 階級チームの5人から作る2人の組(10組)のうち、過去の LTK(S1〜S3)の出場記録で同じシーズンに同じチームだった組の割合(0〜1)。F-010 基準4 と同じ記録を使う
- **メタの近さ m**: m = exp(−(Finale の開幕日 − 共同プレイの最後のシーズンの終了日)の月数 ÷ 12)。共同プレイの組が無ければ m = 0。シーズンの終了日は S1 2025-08-27、S2 2025-12-23、S3 2026-06-21(`docs/research/format-history.md` 節5)。過去のパッチのメタの一覧が無いので経過の月数で近似する(AI の起案)
- **連敗の数 k**: その階級チームの直前の本番から遡って続いた負けの数(勝てば 0)
- **当てはまりの確認**: S1〜S3 の試合日ごとの成績で、その項を入れた場合と入れない場合の対数損失を、試合日を1日ずつ抜いた交差検証で比べること。入れた場合が小さいとき「改善した」とする

## 受入基準

| # | 型 | 受入基準 |
| --- | --- | --- |
| 1 | ユビキタス | システムは大会の全試合(Regular Stage の NEXT・CORE の24試合、MASTERS CUP の12試合、Playoffs の各 GAME)について、試合ごとに両チームの勝率を 0.1% 単位で計算し、両チームの勝率の和を 100.0% にしなければならない |
| 2 | ユビキタス | システムは各試合の対数オッズを、β × (S_A − S_B) + (θ_A − θ_B) + 仕上がりの項の差(基準9)+ 気持ちの補正の差(基準11)+ ドラフトの優位の項(基準14)+ ステージ補正(基準6)で計算しなければならない。S は F-010 の戦力 S(相対評価の前の値)とし、F-010 の相対評価の後の値や強さの軸を足してはならない |
| 3 | ユビキタス | システムは β を、評価設定 `beta.targetSd`(初期値 0.35)と用語の定義から階級ごとに計算し、分析ページに階級ごとの β の値を表示しなければならない |
| 4 | イベント駆動 | 本番の結果またはスクリムの結果が追加されたとき、システムは次の再計算で、試合日までの結果から θ を当て直さなければならない。当て直しは、β × (S_A − S_B) を固定の項として入れた Bradley-Terry を、θ の事前分布(標準偏差 `theta.priorSd` 初期値 0.58)と結果の重み(本番 `weights.official` 初期値 1.0、スクリム `weights.scrim` 初期値 0.25)で当てはめる。F-004 が無い間、システムは θ を 0 とし、分析ページの「結果による更新」の欄を「データなし」と表示しなければならない |
| 5 | イベント駆動 | 試合の分析ページを開いたとき、システムは事前の勝率(β × (S_A − S_B) とステージ補正だけの勝率)と、更新後の勝率(基準2 の全項)を並べて表示し、勝率に効いた項のうち対数オッズの寄与の絶対値が大きい上位3つを、項の名前・対数オッズの寄与・勝率の差(%)とともに表示しなければならない |
| 6 | ユビキタス | システムはステージ補正を、評価設定 `stage.regular`・`stage.masters`・`stage.playoffs`(階級チームごとの対数オッズの加算値。初期値はすべて 0)から加え、分析ページに補正の値と根拠(初期値 0 の根拠は「S1〜S3 でステージ別の差を示すデータが無い」、`docs/design/team-model-algorithm.md` 節3)を表示しなければならない |
| 7 | ユビキタス | システムは作った勝率表を F-001 の入力の形式(`winTable` とステージ別の `stageWinTables`)で出力しなければならない |
| 7b | ユビキタス | システムは各試合の勝率に 80% の区間を付けなければならない。区間は、選手の軸の確度から決まる S の不確かさ(確度 高・中・低・推定に点数の標準偏差 0.5・1.0・1.5・2.0)、β の範囲(`beta.targetSd` を 0.2〜0.6 で一様に引く)、θ の事後分布から、強さを 1,000 回引いて作る。同じ入力と乱数の種からは同じ区間を返す |
| 8 | イベント駆動 | 試合の分析ページを開いたとき、システムはその試合の予測(試合日の前日までの情報で作った勝率)と、確定していれば実際の結果を並べて表示しなければならない |
| 9 | ユビキタス | システムは仕上がりの項を、M × (1 − exp(−d ÷ τ))(M は `maturation.max` 初期値 0.20、対数オッズの単位)で計算し、試合ごとに両チームの値の差を対数オッズに加えなければならない |
| 10 | ユビキタス | システムは仕上がりの速さ τ を、τ = `maturation.tau0`(初期値 1.5 試合日)× (1 + `maturation.a` × (1 − c))× (1 + `maturation.b` × (1 − m))(a・b の初期値 1.0)で計算しなければならない。共同プレイ歴 c とメタの近さ m がどちらも高いチームほど τ が小さくなり、早く仕上がる |
| 11 | イベント駆動 | 本番の結果が追加されたとき、システムは連敗の数 k が2以上の階級チームに、次の試合の気持ちの補正 −min(`mood.cap` 初期値 0.15, `mood.perLoss` 初期値 0.05 × (k − 1))を対数オッズに加え、勝てば 0 に戻さなければならない |
| 12 | イベント駆動 | 試合の分析ページを開いたとき、システムは両チームの仕上がりの項・τ・共同プレイ歴 c・メタの近さ m・経過した試合日の数 d・気持ちの補正・連敗の数 k を表示しなければならない |
| 13 | ユビキタス | システムは基準9〜11 と基準14 の各項について、S1〜S3 での当てはまりの確認の結果(入れた場合と入れない場合の対数損失)を記録し、改善しない項の対数オッズの寄与を評価設定 `unvalidatedCap`(初期値 0.10)以内に切り詰め、分析ページでその項に確度「低」を表示しなければならない。S1〜S3 に材料が無い項(基準14 のプロテクトの項)は「確認できない」と記録し、同じく切り詰める |
| 14 | ユビキタス | システムは CORE の試合のドラフトの優位の項を、δ × (L_B − L_A)(δ は `draft.delta` 初期値 0.20)で計算しなければならない。L_X は、チーム X の CORE の5人の得意チャンピオン(F-010 の用語)のうち、同じカードの直前の NEXT 戦で使われる見込みのチャンピオン(F-006 の NEXT の予想ピックとプロテクト候補。NEXT 戦が確定していれば実際の使用)に当たる数 ÷ 25。F-006 が無い間、システムはこの項を 0 とし、分析ページに「データなし」と表示しなければならない |
| 15 | ユビキタス | システムは本番の結果が入る前の勝率表について、常識の一覧の K-08(NEXT と CORE の階級チーム同士で勝率が 0.80 を超える組が無い)と K-09(勝率が全組 0.45〜0.55 に収まっていない)を検査し、反した場合は勝率表を書かずに、反した組と勝率を列挙して失敗の終了コードを返さなければならない |
| 16 | 望ましくない事象 | 戦力 S を計算できない階級チームがある場合、システムはその階級チームが関わる試合の事前の勝率を 50.0% とし、分析ページに「データ不足」と、S を計算できない理由(評価の無い選手名、または F-010 の計算が無いこと)を表示しなければならない |

各基準には、違反すると失敗するテストが1つ以上必要です。

## スコープ外

- 大会の得点・シード・優勝確率の計算(F-001)
- 指標の収集(F-003)と結果の入力(F-004)
- ピックと作戦の予想そのもの(F-006。この機能はその出力を基準14 で使うだけ)
- 試合中のライブの勝率
- 8軸やロールの重みの、LTK の勝敗による当てはめ(`docs/design/team-model-algorithm.md` 節5.4 で予測が悪化したため)

## 前提

| # | 前提 | 崩れたときの影響 |
| --- | --- | --- |
| 1 | F-010 の戦力 S が計算できる | 基準16 で 50.0% と「データ不足」になる |
| 2 | 戦力 S が試合の強さと相関する(S2・S3 の検証で弱い相関) | 事前の勝率が当たらない。β を広がりで決めるので、相関が弱くても尖りすぎない。RS の3日目の後、事前の項が当て推量より悪ければ `beta.targetSd` を 0.2 へ下げる(技術判断者が決める) |
| 3 | 過去の LTK の出場記録(S1〜S3)と試合日ごとの成績が手元にある | 基準13 の当てはまりの確認ができず、各項は切り詰めた寄与のまま |

## 非機能の要求

| 項目 | 要求 |
| --- | --- |
| 応答時間 | 全試合の勝率と区間の再計算が、作者の PC で 5 秒以内に終わる |
| 再現性 | 同じ入力・同じ基準日・同じ乱数の種で、同じ勝率表と区間を返す |
| 同時実行 | 考慮しない |
| 監査ログ | 再計算ごとに、評価設定の版と基準13・15 の結果をファイルへ残す |
