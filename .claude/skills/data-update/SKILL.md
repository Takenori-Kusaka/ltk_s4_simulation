# 基盤データの更新(共通の手順)

評価(F-009 選手・F-010 チーム・F-005 勝率)の土台になるデータを、出典つきで取り込む手順です。種類ごとのコマンドは、この共通の手順の上に、種類に固有の前処理・抜き出し・統合だけを書きます。

## 種類ごとのコマンド

| コマンド | 取り込むもの | 状態 |
| --- | --- | --- |
| `/input-ts` | 配信・動画の文字起こし(YouTube・Twitch) | あり(`.claude/skills/input-ts/SKILL.md`) |
| `/input-result` | 試合結果(公式の発表、配信の結果画面のスクリーンショット)。スクリムの結果を含む | 予定。F-004(結果の入力)の仕様が承認されてから作る。スクリーンショットの扱い(機械の前処理が無い素材を AI が読むか)もそのときに決める。それまでは `/input-ts` の `matches` に記録を残す |
| (収集) | Riot API のソロキューの試合とランク | あり(`node --env-file=scripts/.env src/collect/cli.ts` → `node src/collect/aggregate-cli.ts`) |
| (経歴の調べ直し) | 選手の最高ランク・プロ歴・他ゲームのプロ歴・競技活動 | 予定(ブランチ `docs/career-research` のマージ後に手順を足す) |

## 原則(すべての種類で守る)

1. **生データはリポジトリの外に置く**。置き場は `data/transcript/`(文字起こし)と `data/raw/`(収集の生データ)。置く前に `git check-ignore -v <ファイル>` で無視されることを確かめる。公開のリポジトリには、自分の言葉で要約した根拠と出典の URL だけを入れる。
2. **前処理は生成 AI を使わない**(文字起こしの場合)。機械で重なりの除去・無関係な部分の除去・名前の対応付けをしてから、AI はその出力だけを読む。AI が生の文字起こしを直接読まない(トークンの節約と再現性のため)。
3. **出典を必ず付ける**。項目ごとに `https://` の URL と、動画なら時刻。URL が分からない根拠は、根拠のファイルにだけ置き、正規化の記録へ統合しない。
4. **別の AI による反証の試みを通す**。抜き出した AI と別の AI が、元の区間・出典と照らして反証を試みる。これは検出の層であり、人の確認でも独立レビュー(G-6。この構成では未達)でもない。記録の値は `aiCheck: not-refuted | refuted | unclear` とし、確かめた担い手(モデルの名称と版)を `aiCheckBy` に残す。`refuted` は根拠のファイルに入れない。`unclear` は根拠のファイルには印を付けて残すが、正規化の記録へは統合しない。確認係には点数に効く主張(要約・時刻・出典に加え、選手の ID・向き・強さ・種類、試合なら種類・相手・結果)を渡し、作成側の推論(`*Basis`・`notes`・`note`)は渡さない。
5. **個人情報を入れない**。次のものを書かない: 本名(ローマ字・漢字・ハングルを含む)、年齢と年齢を推定できる記述(学年・学校段階・始めた年齢)、勤め先と勤め方、私生活、名簿外の一般の人の名前、処分や疑惑の詳細、氏名の入った URL のページ名・スラッグ(別の出典に差し替える)。
6. **見立てを書き込まない**。価値責任者の観察・見立ては「確かめる対象の手がかり」として扱う。AI は、評価設定・常識の一覧・受入基準・雛形の例に、選手やチームを名指しした値や順位を足さない(既存の K-04 の対象者は価値責任者の確定であり、変更は価値責任者が行う)。試合の勝敗は結果の入力(F-004)の材料として記録し、評価の式に手で書き込まない。
7. **話者の推定には確かさを付ける**。自動字幕には話者の情報が無い。話者の確かさは `note` に書き、強さ(strength)を勝手に動かさない。配信者の自チームについての発言には `selfTeam: true`(今の評価のコードは selfTeam を使わない)。名簿の誰かと推定できる呼び名だけを `unmapped` に残し、名簿外の人や評価に関係しない話題は書かない。
8. **人の確認に当たる記録を AI が書かない**。`kind: owner-confirmation` と `collectedBy: human` は、価値責任者が書く記録だけ。AI の取り込みでは `collectedBy: ai` に固定する。価値責任者の確認(例: 「コールしない側」)は、新しい根拠で上書きされない(F-009 基準16・K-04)。

## 共通の流れ

1. **受け取る**: 素材の場所、出典の URL、焦点(何を見たいか)。足りないものは人に尋ねる。待つ間は、PR があれば PR に、まだ無ければ Issue(本文は素材の名前と足りないものだけ)に `state:needs-po` を付ける(コメントだけで済ませない)。
2. **前処理**(機械): 種類ごとのコマンドに書く。
3. **抜き出し**(AI): 前処理の出力を、並列のサブエージェントに分けて読ませる。
4. **反証の試み**(別の AI): 節ごとに。
5. **根拠のファイルを書く**: `docs/research/grounds/` の下。形は種類ごとのコマンドに書く。
6. **統合の前の点数を取る**: 集計のコマンドを一時の場所 `<一時>/before` へ流す(`reference/integrate.md`)。
7. **統合**: 正規化の記録へ足す(`reference/integrate.md`)。
8. **検証**: 集計のコマンドを `<一時>/after` へ流して比べる。`node scripts/gate/g5-local.mjs --no-install` を通す(個々の検査を選んで流さない)。`src/rating/known-facts.json` の常識のうち、保留以外がすべて合格であること。
9. **コミットと公開の前の点検**: ブランチ `docs/input-<種類>-<YYYYMMDD>-<短い名前>` にコミットする(push はまだしない)。`git status --porcelain` が空であることを確かめてから、差分を機械で点検する(`reference/integrate.md` の「公開の前の点検」)。差分に `.claude/guard.json` の testPatterns に当たるファイル(テスト)が無いことも確かめる。点検の結果を依頼者へ示し、確認を得てから push する。依頼者がいなければ push せず、Issue に `state:needs-owner` を付けて渡す。
10. **PR**: **Draft** で出す。本文は `.github/PULL_REQUEST_TEMPLATE.md` から作り、「検証方法と結果」「作成を指示した者」「確定した者」「AI 関与範囲」の「人の確認」は空のまま残す。リスク区分は人が選ぶ。トレーラは PR 本文の末尾の節に1行ずつ置く(`Spec: …` と `Co-Authored-By: <モデルの名称と版>`。コミットの Author は指示した人。規則は `.claude/skills/implement/reference/commit.md`)。根拠・文書だけの PR に付ける `Spec` の値は、規則の解釈が決まっていない(前例は `Spec: setup`。commit.md は setup を設定・ツール・雛形の PR とする)。決まるまでは前例に従い、PR の本文でその旨を書いて確かめる。ラベルの遷移は `.claude/skills/pit/reference/handoff.md` に従う: `state:needs-dev` で出し、CI が緑になってから `state:dev-done`。CI の失敗がリスク区分の欄(人が選ぶ)だけのときは、`state:needs-dev` のまま、区分の選択を人に求める。マージと Ready は人。差し戻し(`state:qm-blocked`)を直したら、CI が緑になってから `state:qm-blocked` を外して `state:dev-done` を付ける。
11. **報告**: 集計の結果・点数の動き・テストの結果は、報告(または PR のコメント)に材料として出し、結論や評価を書かない(`/human-verify` の「出してよいもの」に従う)。確かめられなかったこと、人の判断が要ることを短く伝える。
12. **次の一手**: `node scripts/gate/next.mjs` を流し、「人の判断待ち」が出たらそこで止める。

## 人へ戻す場面(ラベルを付ける)

| 場面 | ラベル | 添えるもの |
| --- | --- | --- |
| データに依存する既存のテストが落ちた(テストは変えない) | `state:needs-po` | 5項目のレポート(形は `.claude/skills/pit/reference/handoff.md`。推奨と決裁事項は人が記入)。テストを変えると決まったら、根拠の PR とは別に、機能仕様のタスクとして `/implement` で行う |
| 常識の検査に反した | `state:needs-po` | 反した条件・選手・軸と、原因の根拠 |
| 出典の URL が分からない | `state:needs-po` | どの素材か |
| 名前の対応・自チームの発言の扱いが決まらない | `state:needs-po` | 候補と根拠 |
| 前処理の辞書を直したい | `state:needs-po` | 改善点の一覧。価値責任者が実装計画へタスクを足してから `/implement` |
| 統合の道具の置き場など技術の判断 | `state:needs-tech` | 選択肢 |
| `.claude/**`(このスキルを含む)の変更 | `state:needs-platform` | 差分の要点 |

## 新しい取り込みのコマンドを足すとき

1. `.claude/skills/input-<種類>/SKILL.md` を作る。frontmatter の `name` と `description`(引数を含める)を書く。
2. 本文には、種類に固有の部分だけを書く: 素材の置き場、前処理、抜き出しの分け方とプロンプト(`reference/` に置く)、根拠のファイルの形、統合先。共通の部分はこのファイルを参照する。
3. 前処理や統合に製品のコード(`src/`・`data/`・`scripts/` の gate・init・vendor 以外)が要るなら、機能仕様のタスクとして実装する(トレーラ `Spec: F-NNN / Task-N`)。
4. 上の表に1行足す。
5. `.claude/**` の変更なので、PR に `state:needs-platform` を付けて AI 維持管理者の確認を受ける。
